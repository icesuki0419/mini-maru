# 이론 과제

## A-1 토큰 재발급 흐름

### 요청 3개가 동시에 401을 받으면?
- A가 먼저 오면 isRefreshing이 false라서 깃발을 들고(81) 재발급을 요청한다(84)
- B,C는 isRefreshing이 true라서 failedQueue에 줄 서서 기다린다(72~78)
- 재발급이 성공하면 B,C도 깨워서 다시 요청한다(85) 그래서 재발급은 한 번만 일어난다


### _retry를 큐에 넣기 전에 표시하는 이유
- `_retry`는 "이미 한 번 다시 보낸 요청"이라는 표시다. 64번 줄은 401이어도 `_retry`가 있으면 재발급하지 않고 포기한다.(103)
- 70번 줄에서 큐에 넣기(72~79) 전에 표시하기 때문에 재발급하러 간 요청뿐만 아니라 큐에서 기다리는 요청도 모두 표시된다.
- 만약 81번 줄 아래에서 표시했다면, 큐에 들어간 요청은 79번 줄에서 빠져나가서 표시가 없다. 다시 보냈는데 또 401이 나오면 처음 실패한 것으로 보고 또 재발급하게 되어 무한 반복될 수 있다.


### REFRESH_EXCLUDED_REQUESTS에 회원가입·인증 요청이 들어 있는 이유
- 재발급은 "로그인했는데 access token만 만료된 경우"에만 의미가 있다. 목록에 있는 요청은 그 상황이 아니라서 60~62번 줄에서 재발급하지 않고 바로 실패시킨다.
- 재발급 요청 : 84번 줄에서 재발급할 때 `isRefreshing`이 이미 `true`라서, 이 요청이 401을 받으면 72번 줄에서 큐에 들어가 자기 자신의 재발급이 끝나길 기다리게 된다. 그러면 영원히 끝나지 않는다.
- 로그인 : 여기서 401은 토큰 만료가 아니라 비밀번호가 틀렸다는 뜻이라 재발급해도 소용없다.
- 회원가입, 인증번호, 비밀번호 변경 : 로그인하기 전에 하는 요청이라 재발급할 토큰이 없다. 재발급을 시도하면 실패하면서 92~95번 줄의 세션 만료 알림이 엉뚱하게 뜰 수 있다.
- 모르는 부분 : 비밀번호 변경이 로그인 전 비밀번호 찾기용인지, 로그인 후 비밀번호 변경용인지는 확인하지 못했다.


## A-2 QueryClient를 useState 안에서 만드는 이유

### useState 안에서 만드는 이유
- `QueryClient`는 서버에서 받은 데이터를 보관하는 캐시다. (`apps/user/src/services/QueryClientProvider.tsx` 16~25)
- 컴포넌트 안에 그냥 `new QueryClient()`를 쓰면 리렌더링될 때마다 새로 만들어져서 캐시가 사라진다.
- `useState(() => new QueryClient())`는 처음 한 번만 만들고 그후에는 같은 객체를 계속 돌려준다.
- `() =>`로 감싸는 이유 : 감싸지 않으면 매 렌더링마다 객체를 만들었다가 버리는 낭비가 생긴다.

### 모듈 최상단에서 만들면 생기는 문제
- Next.js는 `'use client'` 컴포넌트도 서버에서 한 번 렌더링한다.
- 서버에서 모듈 최상단 변수는 모든 사용자의 요청이 함께 쓴다. 그래서 캐시 하나를 여러 사용자가 공유하게 되어 다른 사용자의 데이터가 섞여 보일 수 있다.
- `useState` 안에서 만들면 요청마다 따로 만들어져서 이런 문제가 없다.
- 실습 코드 `src/app/Providers.tsx`도 같은 방식으로 만든다.


## A-3 성적 계산 

### 실제 마루의 계산 방법 요약
총점 = 교과 + 출결 + 봉사 + 가산점
- 교과: 기본점수 + (2-1 평균 + 2-2 평균) × 4.8 + 3-1 평균 × 14.4 + 정보 교과 점수
  - 수학은 2배로 반영한다(85, 96).
  - 국어·영어·수학이 F면 C로 보고, 다른 과목의 F와 `-`는 평균에서 뺀다.
  - 정보 교과는 1학년 성적까지 포함한 평균 × 0.5, 성적이 없으면 C로 계산한다.
- 출결 : 결석 + (지각+조퇴+결과)÷3을 결석 수로 보고 18점에서 1회당 1점 뺀다. 16회 이상이면 0점이다.
- 봉사 : 15시간 미만 0점, 30시간 초과 18점, 그 사이는 모자란 1시간마다 0.5점씩 뺀다.
- 가산점 : 자격증 중 가장 높은 점수 + 멘토링 1점, 최대 4점이다.

### 실습의 단순화된 규칙과 다른 점
1. 학기 비중 : 실습은 3:3:4 가중 평균이지만 실제는 2-1·2-2에 4.8, 3-1에 14.4를 곱해서 3-1 비중이 훨씬 크다.
2. 과목 : 실습은 5과목을 똑같이 보지만 실제는 수학을 2배로 반영하고 정보 교과를 따로 계산한다.
3. 출결 : 실습은 15점에서 결석 1회당 3점을 빼지만 실제는 18점에서 1점씩 빼고 16회 이상이면 0점이다.
4. 봉사 : 실습은 3구간이지만 실제는 15~30시간 사이를 0.5점 단위로 계산한다.
5. 가산점 : 실습에는 없지만 실제는 자격증과 멘토링 가산점이 있다.


## A-4 원서 atom 

### atom 역할 정리
- 원서 내용
  - `formAtom` : 지원자·보호자·학력·성적·자기소개서·전형을 한 객체로 보관
  - `subjectListAtom`, `GEDSubjectListAtom`, `newGEDSubjectListAtom` : 교과·검정고시 과목 목록
- 진행 단계
  - `formStepAtom` : 현재 원서 단계, `formGradeStepAtom` : 성적 입력 안의 하위 탭
  - `correctAtom` : `utils/formStep.ts` 29번 줄에서 단계 이동 후 `false`로 되돌린다. 정확한 의미는 확인하지 못했다.
- 파일
  - `profileAtom` : 증명사진 파일, `formProfileAtom` : 증명사진 업로드·다운로드 URL
  - `finalFormAtom` : 최종 제출 서류 파일
  - `formDocumentAtom` : 서류 파일명·URL. stores 밖에서 사용하는 곳을 찾지 못했다.
- 임시저장
  - `lastSavedFormAtom` : 마지막으로 저장한 원서, `isSaveFormLoadedAtom` : 임시저장을 불러왔는지 여부

### 여러 atom으로 나눌 때와 하나로 합칠 때
- 나눌 때 장점 : 컴포넌트가 필요한 atom만 구독하므로 그 값이 바뀔 때만 리렌더링된다. 역할이 분명하다.
- 나눌 때 단점 : 개수가 많아서 로그아웃 등으로 초기화할 때 일부를 빠뜨리기 쉽다.
- 합칠 때 장점 : 저장·초기화·서버 전송을 한 번에 할 수 있다.
- 합칠 때 단점 : 일부만 바뀌어도 그 atom을 쓰는 모든 컴포넌트가 리렌더링된다. 수정할 때 객체를 복사해야 해서 실수하기 쉽다.
- 마루는 서버로 한 번에 보내는 원서 내용은 `formAtom` 하나로 합치고, 화면 상태와 파일은 나눴다.
- 실습 코드 `src/stores/form.ts`도 원서 내용과 단계, 저장 상태를 나눴다.


## A-5 원서 단계 전환 

### 단계는 어떻게 바뀌나
- 주소는 항상 `/form` 하나이고, `formStepAtom`에 "지금 몇 단계"를 저장한다.

### URL로 나누는 방식과 비교
- atom 방식 장점 : 주소로 단계를 건너뛸 수 없어서 앞 단계 검사를 꼭 거친다. 입력 내용이 그대로 유지된다.

- URL 방식 장점 : 뒤로가기와 새로고침이 자연스럽다.
- URL 방식 단점 : 주소로 중간 단계에 바로 들어올 수 있어서 막는 코드가 따로 필요하다.
- 실습 코드도 `src/stores/form.ts`의 `formStepAtom`으로 같은 방식을 쓴다.



## B-1 서버 컴포넌트와 클라이언트 컴포넌트

서버 컴포넌트는 서버에서 화면을 다 만들어서 보내 준다. 가볍고 빠르지만 버튼 클릭이나 입력 같은 상호작용은 할 수 없다. 클라이언트 컴포넌트는 파일 맨 위에 `'use client'`를 쓰고, 브라우저에서 실행되어 `useState`, `onClick`, `localStorage`를 쓸 수 있다. 대신 브라우저가 JavaScript를 더 내려받아야 한다. Next.js App Router는 기본이 서버 컴포넌트다.

실습 코드에서 `src/app/layout.tsx`는 서버 컴포넌트다. 페이지 제목만 정하고 누를 것이 없기 때문이다. 원서 작성, 로그인 같은 페이지는 입력과 버튼 클릭이 있고, `localStorage`에서 토큰을 읽어야 해서 `'use client'`를 두었다. `Providers.tsx`도 `useState`로 `QueryClient`를 만들기 때문에 클라이언트다.

-> 사용자가 누르거나 입력하는 것이 있으면 `'use client'`를 두고 보여주기만 하면 서버 컴포넌트로 두면 된다.


## B-2 React Query의 staleTime, gcTime, invalidateQueries, setQueryData

React Query는 서버에서 받은 데이터를 캐시에 보관한다. `staleTime` 동안은 서버에 다시 요청하지 않는다. `gcTime`은 그 데이터를 쓰는 화면이 없을 때 캐시에서 지우기까지 기다리는 시간이다.

`invalidateQueries`는 데이터가 바뀌었지만 새 값을 정확히 모를 때 쓴다. 해당 데이터를 오래됨으로 표시해서 서버에 다시 요청하게 한다. `setQueryData`는 서버 응답 등으로 새 값을 이미 알고 있을 때, 다시 요청하지 않고 캐시를 직접 바꾼다.

`src/app/Providers.tsx` 28번 줄에서 `staleTime`을 5분으로 정해서, 5분 안에는 같은 데이터를 다시 요청하지 않는다. `src/services/form/mutations.ts` 31번 줄은 원서 제출이 성공하면 `invalidateQueries`로 원서 상태를 다시 불러오게 한다. 제출하면 상태가 바뀌지만 프론트가 새 상태를 직접 알 수는 없기 때문이다.

다만 여기서 무효화하는 queryKey는 `['form', 'status']`인데 상태를 불러오는 `src/services/form/queries.ts` 7번 줄의 queryKey는 `['formStatus']`라서 서로 맞지 않는다. queryKey를 문자열로 여러 곳에 직접 쓰면 이런 실수가 생기기 쉬우므로 queryKey를 한 파일에 모아 관리하는 것이 좋다.


## B-3 useState, Jotai atom, React Query — 상태를 어디에 둘까

먼저 원본이 서버에 있는 데이터면 React Query에 둔다. 캐시, 다시 불러오기, 로딩/에러 상태를 React Query가 관리해 준다. 그리고 서버 데이터가 아니면서 여러 컴포넌트가 함께 쓰면 Jotai atom에 둔다. 한 컴포넌트에서만 쓰면 `useState`로 충분하다.

실습 코드 분류
- React Query : 내 정보, 일정, 원서 상태, 임시저장, 학교 검색, 결과 모두 서버에 원본이 있다.
- Jotai atom : 작성 중인 원서, 현재 단계, 불러왔는지 여부, 마지막 저장 시각 원서 단계 컴포넌트 7개와 진행 버튼이 함께 쓴다.
- useState : 로그인 입력값, 학교 검색어와 선택, 개발 패널 열림 여부 그 컴포넌트 안에서만 쓴다.

atom과 React Query 캐시는 컴포넌트가 사라져도 남는다. 그래서 사용자가 바뀌는 로그아웃 때 직접 비워야 한다. 문의 4번은 이 초기화를 빠뜨려서 이전 사용자의 원서가 보인 버그였다.


## B-4 리렌더링 조건과 useMemo·useCallback

컴포넌트는 세 가지 경우에 다시 렌더링된다. 자신의 상태가 바뀔 때, 부모 컴포넌트가 다시 렌더링될 때, 구독하는 데이터가 바뀔 때다.

`useMemo`는 의존하는 값이 바뀌지 않으면 계산 결과를 재사용하고 `useCallback`은 함수를 매번 새로 만들지 않고 같은 함수를 재사용한다. 계산이 무겁거나, `React.memo`로 감싼 자식에게 넘기는 값,함수라서 참조가 같아야 할 때, `useEffect`의 의존성으로 쓰일 때 필요하다. 반대로 가벼운 계산이나 평범한 `onClick` 함수에 쓰면 메모하는 비용만 늘어서 필요 없다.

실습 코드에는 `useMemo`, `useCallback`이 쓰이지 않았다. 예를 들어 `src/components/form/GradePreview.tsx` 11번 줄은 렌더링마다 `calculateScores(form)`로 성적을 다시 계산한다. 성적 입력 중에는 입력할 때마다 `formAtom`이 바뀌어 다시 렌더링되지만 5과목 × 3학기 정도의 가벼운 계산이라 `useMemo`가 필요 없다. 게다가 의존 값인 `form`이 입력할 때마다 바뀌므로 메모해도 매번 다시 계산하게 되어 이득이 없다. 성능 문제가 실제로 보일 때 측정하고 적용하는 것이 맞다고 판단했다.


## B-5 토큰 저장 위치와 보안 (XSS, CSRF)

XSS는 공격자의 스크립트가 우리 사이트 안에서 실행되어 브라우저에 있는 정보를 훔치는 공격이다. CSRF는 다른 사이트가 사용자의 브라우저를 이용해 우리 서버로 요청을 보내는 공격으로 쿠키가 요청에 자동으로 붙는 점을 이용한다.

- localStorage : JavaScript로 언제든 읽을 수 있어서 XSS에 약하다. 요청에 자동으로 붙지 않으므로 CSRF에는 안전하다.
- 일반 쿠키 : `document.cookie`로 읽을 수 있어 XSS에 약하고 요청마다 자동으로 붙어서 CSRF에도 약하다.
- httpOnly 쿠키 : JavaScript가 읽을 수 없어서 XSS로 토큰을 훔칠 수 없다. 자동으로 붙어서 CSRF 위험이 있으므로 `SameSite` 설정이나 CSRF 토큰으로 막아야 한다.

`src/utils/token.ts` 1~16번 줄은 access token과 refresh token을 모두 localStorage에 저장한다. 실제로 개발자 도구 Application 탭에서 두 토큰이 그대로 보였고 문의 3번을 검증할 때 값을 직접 바꿔 볼 수도 있었다. 이는 XSS 스크립트도 같은 방법으로 토큰을 읽을 수 있다는 뜻이다. 특히 refresh token은 유효시간이 1일이라 탈취되면 피해가 크다. 실제 서비스라면 refresh token은 httpOnly + `SameSite` 쿠키로 서버가 관리하고 access token은 짧게 유지하며 메모리에 두는 방식이 더 안전하다고 생각한다.
